# ADR-0015: Synthetic telemetry storage and anomaly policy

- **Status:** Accepted provisionally for synthetic QA (2026-11-15); review against the missing master spec is required.
- **Context:** Phase 07 needs repeatable fictional sensor-like series, measured anomaly behavior, tenant-safe time-series reads, and alerts in the canonical event stream. The prior ADR deferred time-series storage and no real PLC/SCADA access is authorized.
- **Decision:** A seeded standard-library simulator emits pressure (kPa), flow (m3/h), vibration (mm/s), and temperature (degC) for the synthetic pump fixtures. It adds deterministic noise, missingness, independent quality flags, and explicit holdout fault labels stored separately from public samples. No external MQTT broker or plant connection is used. Samples enter an additive PostgreSQL derived table through validated bounded batches with tenant/site/asset/metric/timestamp keys. PostgreSQL `date_bin`/`generate_series` provides bounded downsample buckets. A manual, fixture-only 90-day prune command is provided; no scheduled deletion runs.
- **Detector and alerts:** The baseline is frozen to each series' initial 30 valid samples; robust z-score uses median/MAD scaling and flags absolute score >= 6. No LLM predicts measurements. An alert requires at least 3 scored anomalies among the latest 5 valid observations, with a 15-minute per-asset/metric cooldown. A deterministic UUID incident is appended as an internal `incident.created` event through trusted server-side event-store code; the public device-sync source policy is unchanged. Alert event IDs and database uniqueness make replay idempotent.
- **Access and data boundaries:** Auth and App Check remain required. The telemetry API repeats membership/site authorization, caps queries at 30 days and 10,000 downsample buckets, applies per-actor rate limits, and marks gaps, availability and stale data. Hidden holdout labels and fault types are never inserted into Postgres or returned by API responses. The `/telemetry` chart uses that authenticated API.
- **Migration impact:** Contract v1.3.0 adds telemetry sample/series response schemas and the authenticated `/v1/world/telemetry` API while retaining prior schema validation. Additive `004_synthetic_telemetry.sql` adds `telemetry_samples` and `telemetry_alerts`, keyed and constrained to the demo tenant/fixture. No existing records are rewritten. The sample table is derived/reproducible; canonical incident events remain durable. Rollback is application rollback plus a reviewed forward migration; dropping tables is not an automatic rollback.
- **Consequences:** Timescale is not required; retention cleanup is explicit and scoped. Out-of-order arrival is accepted because primary keys are timestamp-based; duplicate samples are ignored. The detector's measured synthetic false positives remain visible in evidence. MQTT, Timescale, online model inference, and real equipment integration are out of scope.
- **Verification boundary:** Unit/schema tests and deterministic holdout metrics do not verify SQL constraints, real API query plans, batch persistence/idempotence, alert/event atomicity under crashes, or retention on a live database. Docker/Postgres is required to close those gates.
