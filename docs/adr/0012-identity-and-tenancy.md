# ADR-0012: Firebase identity and organization tenancy

- **Status:** Accepted provisionally (2026-11-15)
- **Context:** Browser identity is Firebase Authentication, but client role claims are not an authorization source. Canonical organization membership, site scope, device registrations, invite hashes, rate limits, and upload approvals must be tenant scoped and server controlled. Firestore is a derived projection for browser rules; Storage access depends on that projection and an explicit artifact authorization.
- **Decision:** Verify Firebase ID tokens on every protected API request with revocation checks. Verify App Check tokens independently and compare the verified app ID with `FIREBASE_APP_ID`. Require the project and app IDs in production; reject production bypass and all production emulator configuration at startup. Resolve role and site scope from PostgreSQL on each request. Keep organization membership as a composite `(organization_id,user_id)` key, site grants as composite foreign keys, and device identities bound to an organization and user. Device registration proves possession of an ECDSA P-256 or Ed25519 key against a one-use five-minute nonce. Device revocation is canonical in PostgreSQL.
- **Projection policy:** Firestore contains only server-written membership/site scope and upload-authorization documents. Rules deny all client writes, require active membership and site scope, and default-deny unknown paths. Storage rules require an approved, unexpired authorization matching user, site, MIME, classification, and size; object updates/deletes are denied. PostgreSQL is authoritative; Firestore/Storage projections must fail closed. Production invite delivery is disabled until a verified-email provider exists; local/test receives one-time invite tokens from the API.
- **Offline policy:** Cache only the prior authorized profile for a finite eight-hour lease. Display is read-only and never grants API access. No first-time offline login.
- **Operational boundary:** App Check bypass can only be enabled in local/test; local additionally requires loopback Auth emulator. Emulators test rules only, not real App Check, production IAM, or Firebase token validation. Use workload identity rather than service-account key files.
- **Consequences:** Additive identity schema migration `0002_identity`; migration downgrade deliberately refuses destructive rollback. Restore prior state from backup and use a reviewed forward migration for rollback. Existing `001_core` event tenancy remains in `tenants`; organization IDs must be provisioned consistently with tenant IDs before event/simulation APIs are used. Firestore projection reconciliation/retry and production invite mail delivery remain future work.
- **Migration impact:** Adds `organizations`, `identity_users`, `sites`, `memberships`, `membership_sites`, `devices`, `device_challenges`, `organization_invites`, `invite_sites`, `identity_rate_limit_buckets`, and `upload_authorizations`. No app identity rows existed before this migration. Updating roles, scopes, or status also updates membership projections; privileged reductions update Firestore before committing canonical state.
- **Review note:** The required product reference files are absent from this checkout; this decision is provisional and must be reconciled with the master spec and privacy requirements when restored.
